# BUG-001 — Streamlink Bridge 0.1.0 reportedly does not work

Status: OPEN / UNREPRODUCED (user report accepted). Severity: blocks replacing the installed Bridge with copied code.
Environment: Apple M4 Apollo, IINA 1.4.4, Streamlink 8.6.3, mpv 0.41.0, yt-dlp 2026.08.19. Date: 2026-11-07.

## Known observations
The installed plugin lives at ~/Library/Application Support/com.colliderli.iina/plugins/local.iina.streamlink-bridge.iinaplugin. Manifest uses entry: main.js and globalEntry: global.js, with file-system and show-alert permissions. The per-player main.js is effectively empty; global.js creates three menu commands and starts Streamlink via iina.utils.exec and iina-cli.
Static syntax and manifest JSON passed earlier. The user reports the deployed implementation does not work. No evidence has yet established whether the menu appears, if click handler runs, whether Streamlink starts, or whether the playback process remains attached. Native terminal Streamlink-to-IINA playback succeeded on other channels before this report; irrelevant to plugin functionality.
The official IINA dev guide and installed known-good packages use globalEntry, while a different official documentation page shows global; this inconsistency is NOT evidence that the deployed key is wrong. Runtime observation is needed.

## Diagnose in this order, using minimal disturbance
1. Capture current plugin files and versions for a reproducible fixture; do not alter installed files.
2. Open IINA's Window > Log Viewer, filter global - Streamlink Bridge and plugin initialization; record whether plugin loads/errors. Plugin > Developer Tool may inspect menu and util availability on IINA 1.4.4.
3. Observe whether Plugin menu contains any Bridge action. Record actual result; do not infer.
4. Click a single action with a valid hutchmf URL while live; observe IINA UI and Streamlink process list, error messages, log; no Safari interruption.
5. Check output args; compare Streamlink CLI command with documented --player and --player-args --stdin; verify quality strings.
6. Close only the test window and verify all associated child processes stop, that unrelated IINA windows remain.
7. Identify smallest root-cause fix and add a regression test. Label suspected versus confirmed causes.

## 2026-11-07 follow-up: evidence acquired; original click path still unresolved
The installed Bridge package matches the preserved source byte-for-byte. CLI `iina-cli --help` confirms it normally exits immediately after invoking the app; a lifetime problem with the original `streamlink --player=iina-cli --stdin` path remains plausible but **not directly reproduced as the old plugin's fault**.
The new development plugin's `globalEntry` demonstrably ran and created a hutchmf IINA player, so a missing/incorrect `globalEntry` key is not the likely generic blocker. The new plugin's player recorded `file-started` and `file-loaded` events, but its early 14-second automatic test stop was a confounder and has been removed.
**Critical independent fault:** IINA 1.4.4 build 168 on macOS 27.2 (26B123) generated five EXC_BREAKPOINT/SIGTRAP reports at `PlayerCore.startMPV()`. The first two predate the dev plugin. See `INVESTIGATION-2026-11-07.md` and `evidence/tests/crash-summary-2026-11-07.txt`. Do not claim a root cause solely from the stack or conflate scripted stop with app crash.
As a precaution development plugin was disabled and the auto-start trigger removed. M1 acceptance remains blocked by observed app crashes and absent prolonged real-UI play/stop evidence.
