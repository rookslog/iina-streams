## Confirmed platform rules (check current official docs again before applying)

- Codex configuration precedence: CLI overrides > trusted project `.codex/config.toml` > selected `--profile` > user `~/.codex/config.toml` > managed/system/default. Untrusted projects skip project config/hooks/rules; user defaults still apply.
- Codex discovers skills from repo `.agents/skills`, user `~/.agents/skills`, `$CODEX_HOME/skills`, and bundled/plugin sources. Skills use metadata-first progressive disclosure. `[[skills.config]]` selectors by name/path can disable individual skills; `[skills.bundled] enabled=false` disables bundled skills, NOT all user-level skills.
- Codex **subagents inherit the parent's skill availability** by default. Each custom agent TOML can narrow it via `[[skills.config]]`, `[skills.bundled]` and `[skills] include_instructions=false`; can disable `features.plugins`, `features.memories`, etc. Custom-agent sandbox, provider, MCP settings do NOT override the parent's. Instruction-only read-only promises are not separate sandbox enforcement. *[Audit correction: per-agent `skills.config` and the sandbox non-override are supported by the docs. `skills.include_instructions` and `features.plugins` were **not found** on the subagent docs pages read, so treat them as unchecked until a runtime probe confirms them. The render also shows all agents share one working directory, and full-history forks cannot override model or effort.]*
- Plugin enablement can be overridden in a trusted project's config, e.g. `[plugins."superpowers@openai-curated"] enabled=false`. This is distinct from individual skill filtering. *[Audit correction: this project-level `[plugins."…"]` override was **not found** on the config-basic or build-skills pages read; it is unchecked, not confirmed.]*
- Alternate `CODEX_HOME` separates Codex config/auth/history/cache and Codex-home skills, but can require its own authentication/setup and does not inherently prevent discovery of `$HOME/.agents/skills`. Avoid treating it as a one-line complete sandbox.
- Claude Code differs: `skills:` in subagent frontmatter **preloads complete skill bodies**; it does not define the only skills the subagent could access. Without preloading, the Skill tool can still discover available user/project/plugin skills. To prevent access, deny or remove `Skill` for that agent. Claude subagents can constrain tool access by `tools`/`disallowedTools`, use `permissionMode: plan`, and omit inherited CLAUDE.md files when supported. Claude user settings, project settings and enabled plugins are separate layers.
- Hook enablement is not evidence a hook fired. Verify actual event definitions, trusted hashes, launch profile, matchers, exit behavior and evidence logs. Avoid a broad high-latency Stop hook or every-edit design review unless justified.

## Recommended lightweight architecture (not yet enabled)

**A. Sol lead:** The permanent context contains project `AGENTS.md` (short), the specific handoff, ownership/safety rules and 3–5 task-specific skills made available on demand; never force full Superpowers, Pocock and P Stack process routers simultaneously. Keep the lead responsible for requirements, decisions, integration and native acceptance. The user-level global AGENTS.md still loads unless separately isolated/refactored. Prefer a trusted project override that disables globally irrelevant skills and Superpowers for this repository, without modifying global config.

**B. Independent UX critic:** A small role with Apple HIG references, original TNF design work and `streams-interaction-design`; no engineering delegation, tools, external auth or native app modification. When running Claude Opus outside Codex, explicitly supply the references and use a restrained tool/Skill policy; no assumption that it magically inherits Codex skills.

**C. Implementer:** Only `tdd` / `codebase-design` / optional `streams-interaction-design` in its visible skill catalog. Assigned isolated file ownership and focused tests. No native app/window, credential or deployment actions.

**D. Native QA:** Primarily `streams-native-acceptance`, plus minimal IINA fixture commands and timestamped evidence. Single exclusive operator to avoid multiple agents driving the same GUI. Avoid generic design/engineering workflow skills.

**E. Auth/replay reviewer:** Primarily `streams-auth-replay` and `security-review`; read-only input boundary, no tokens, no OAuth grants, and separate authentic/public-source evidence.

**F. Documentation researcher:** No skill needed by default. Limit to primary documentation/actual pinned code and a short evidence return. A specialized skill may be added only if repeated failures justify it.

### Strong isolation options

1. **Trusted repo project-filter (recommended first)**: explicitly disable all discovered irrelevant user skills with absolute-path selectors and disable `superpowers@openai-curated` in project config. Make the project skill catalog a tested, small union of roles (approximately 6–9). Then subtract role-irrelevant skills in custom-agent TOML. A cap on `skills.max_context_tokens` is NOT a filter: it merely truncates the descriptions; do not use it as a substitute.
2. **Role-specific catalog suppression**: for critique/research agents, `[skills] include_instructions=false` can remove the automatic available-skills instructions, while the agent receives only explicit source documents in its task. Pair with `features.plugins=false` where capability reduction is desired. This is context suppression, not a guarantee the files cannot be accessed via shell/file reads.
3. **Dedicated external process/harness**: use a separately launched Codex/Claude instance with isolated config and controlled tools when truly independent permissions/skill scope or external Opus judgment is required. Different `CODEX_HOME` requires deliberate auth/state management; do not automatically rewrite HOME or copy credentials.

### Minimal intended validation, before claiming isolation

1. Verify repo trust and inspect current project's resolved config/profile/plugins. Compare the candidate list this document predicts with the exact catalog in a fresh Codex session (not solely the model's self-report).
2. Probe an excluded global skill by asking whether it is available and trying explicit invocation; it should fail to resolve. Probe an included project skill; it should load when invoked.
3. Spawn exactly one UX-critic and one implementer test subagent. Inspect their available skills/tools and confirm plugin/tool restrictions. Confirm that each received the short project guidance and no unrelated broad workflow.
4. Verify hooks with a harmless edit in a disposable, isolated test file: check exact event fire count, duration and output. Do not launch app, revoke credentials or touch stable plugins.
5. Only after the loadout works, compare like-for-like IINA tasks across a minimal baseline, a curated loadout, and a Superpowers-full alternative. Use objective native outcome, regressions, time, resource and model/tool overhead. One apparent win cannot establish general efficacy.

## Evidence assessment

SkillsBench (Feb 2026, 7,308 trajectories) reports +16.2 percentage points on average for curated skills but only +4.5 points for software engineering; 16/84 tasks regress, and self-generated skills do not help on average. This is a benchmark of particular tasks/models/harnesses, **not proof** that Apple Design, Matt Pocock, Superpowers or our new IINA skill improves GPT-6.1 Sol. Maintainer adoption, stars and independent issue reports indicate community support, not task-specific causal effectiveness. Prefer bounded local task A/B comparisons to generic rankings. *[Audit correction: these figures are from an older SkillsBench version. v4 (2026-06-14) reports 87 tasks, +16.6pp overall (range +4.1 to +25.7pp by configuration) and **Software Engineering +11.6pp (N=16)**, the last from Table 3 via a summarized page tail. The independent audit (§6 R5) also questions whether native A/B comparisons are feasible here.]*

**Priority:** verify actual loading, then simplify. The existing project-local harness scaffolding is a draft; do not call it isolated, finished, or validated until these checks pass.
