# Twitch follows beyond the documented API (2026-11-22)

Research for the operator's question: if someone is signed in, what can Streams read about the channels they follow, with what status, and in what order? Written by a Claude research agent (Sonnet 5.5, high effort as requested by the lead). Started 20:03 EST, finished 20:12 EST. No code changed. No request carried a token, no request went to `gql.twitch.tv`, and the operator's Twitch session and cookies were not touched.

Builds on `docs/design/DISCOVERY-AND-PLATFORMS-2026-11-22.md` §2.2 (Helix Get Followed Streams: live only, descending by viewers; Get Followed Channels: all follows, newest `followed_at` first, no live field). Those are not re-derived here.

## Labels and terms

- **READ** means a page or file was read in this session. A link follows. Source links are GitHub permalinks pinned to the commit I read, so line numbers stay valid.
- **INFERRED** means I reasoned from what I read. It was not observed.
- **UNCHECKED** means I did not look, or could not without breaking a rule above.
- **Helix** is Twitch's documented REST API at `api.twitch.tv/helix`. **GQL** is the GraphQL endpoint `gql.twitch.tv/gql` that twitch.tv's own pages call; Twitch does not document it.
- **Persisted query**: the web client sends a fixed operation name plus a SHA-256 hash of a query stored on Twitch's side, instead of query text. A hash can stop working when Twitch changes the query.
- **Client-Integrity token** (header `Client-Integrity`): a signed token a browser computes with Twitch's bot-detection script, passed on some GQL calls.
- **First-party token**: an OAuth token issued to one of Twitch's own clients (twitch.tv web, Android app, Android TV app), as opposed to one issued to Streams' own registered app.
- **Device-code sign-in**: the flow where the app shows a short code and the user types it at `twitch.tv/activate`. Streams uses it today with its own app.

## Summary

1. Twitch itself states the order of the signed-in sidebar: sponsored live channels first, then other live channels, then offline channels "in order of the number of new videos available". It does not say how live channels are ordered among themselves (READ, §Q1).
2. A personalised "likely to watch" sort of the follows list is not in Helix. In GQL the `followedLiveUsers` field accepts a `sort` argument whose values include `RELEVANCE`, but no client I read uses that value, and I found no source showing it returned (READ for the argument; INFERRED and untested that it personalises).
3. Every third-party client I read that lists follows either uses Helix with its own app token (Frosty, Chatterino), or uses GQL with a first-party token captured from a web or TV sign-in (Xtra, SmartTwitchTV), or keeps a local list (Twire). I found none that shows an app-registered token working against GQL follows.
4. Twitch's Developer Services Agreement, which loads with `curl --compressed`, says developers "will only access Program Materials documented on the Twitch Developer Site"; whether GQL falls under that is an interpretation (READ clause, INFERRED reach, §Q4).
5. With our own token and `user:read:follows`, Streams can show live/offline, viewers, title, category, start time and, for offline channels, follow date; it cannot show Twitch's own order. Closer to that order costs a first-party sign-in, the Terms risk, and breakage when hashes change, with no source proving the order is reachable even then (§Q5).

## Q1. How twitch.tv's own sidebar gets the list and orders it

**Order, from Twitch's own text.** The "Recommendations On Twitch" page, last modified 2025-09-22, says that in the left navigation, for a signed-in user, "live channels streaming sponsored content via Twitch sponsorships" are listed first, "followed by other live channels, and then offline channels in order of the number of new videos available". It adds that for the left navigation, browse page and search, "live channels are more frequently given higher priority than non-live channels". It says the browse directory can be sorted "by the number of viewers or by Twitch's recommendations", and that recommendations use device, engagement, language, login state, region, watch history and age (READ: https://legal.twitch.com/legal/recommendations-on-twitch/). The page does not say what orders the "other live channels" block, so that stays open.

**History of the order.** In December 2020 Twitch Support announced an experiment to "sort the channels based on viewing behavior instead of view count", as quoted in a news article (READ, secondary: https://www.dexerto.com/entertainment/twitch-experimenting-with-new-way-to-customize-followed-channels-lists-1476766/). A userscript that re-sorted the sidebar by viewer count now carries an "OBSOLETE: Twitch has finally added the ability to change the sorting" note (READ: https://github.com/tomasz13nocon/twitch-sort-by-viewcount/blob/master/README.md). Neither says what the options are called today.

**The exact sort options the web UI offers: unread.** I did not open twitch.tv (that would use the operator's session), and neither a web search nor a GitHub code search turned up the option labels. I cannot confirm "Recommended for you" or "Viewer count" as menu text.

**GQL operations.**
- `SideNav` is the persisted query Xtra (an open-source Android Twitch client) sends to get the sidebar's recommended sections. Its variables carry `isLoggedIn` and a `recommendationContext` with `platform: "web"`, and Xtra picks the shelf with id `provider-side-nav-similar-streamer-currently-watching-1` out of the response (READ: [GraphQLRepository.kt:982](https://github.com/crackededed/Xtra/blob/0ab697de04799365f590f91e2dfbefc092c3ad5a/app/src/main/java/com/github/andreyasadchy/xtra/repository/GraphQLRepository.kt#L982), [ChannelSuggestionsDataSource.kt:24](https://github.com/crackededed/Xtra/blob/0ab697de04799365f590f91e2dfbefc092c3ad5a/app/src/main/java/com/github/andreyasadchy/xtra/repository/datasource/ChannelSuggestionsDataSource.kt#L24)). That is the recommended-channels shelf, not the followed list.
- `FollowingLive_CurrentUser` is the persisted query for the live part of the Following page. Xtra sends it (READ: [GraphQLRepository.kt:1308](https://github.com/crackededed/Xtra/blob/0ab697de04799365f590f91e2dfbefc092c3ad5a/app/src/main/java/com/github/andreyasadchy/xtra/repository/GraphQLRepository.kt#L1308)), and so does SmartTwitchTV, an Android TV client, with `followedLiveUsers(first:100 …)` and no sort (READ: [ScreensObj.js:75](https://github.com/fgl27/SmartTwitchTV/blob/7ca7b76249b4c2a6b2f44932641f49894410c99a/app/specific/ScreensObj.js#L75)). Whether this is the exact call behind the sidebar is UNCHECKED.
- `ChannelFollows` lists all follows with an `order` of `ASC` or `DESC` (READ: [GraphQLRepository.kt:1345](https://github.com/crackededed/Xtra/blob/0ab697de04799365f590f91e2dfbefc092c3ad5a/app/src/main/java/com/github/andreyasadchy/xtra/repository/GraphQLRepository.kt#L1345)). The older field form `user.follows(order:)` returns `followedAt` and `lastBroadcast.startedAt` per channel (READ: [UserFollowedUsers.graphql](https://github.com/crackededed/Xtra/blob/0ab697de04799365f590f91e2dfbefc092c3ad5a/app/src/main/graphql/UserFollowedUsers.graphql)).
- `PersonalSections` appears in a 2021 trace of the operations twitch.tv sends on first load, beside `TopNav_CurrentUser` (READ, dated: https://wundergraph.com/blog/graphql_in_production_analyzing_public_graphql_apis_1_twitch_tv). I read it as a sidebar-sections call (INFERRED from position and name, from 2021).

**The sort argument.** `followedLiveUsers(first, after, sort: StreamSort)` exists, with `StreamSort` = `VIEWER_COUNT`, `VIEWER_COUNT_ASC`, `RECENT`, `RELEVANCE` (READ in Xtra's hand-maintained schema: [schema.graphqls:393](https://github.com/crackededed/Xtra/blob/0ab697de04799365f590f91e2dfbefc092c3ad5a/app/src/main/graphql/schema.graphqls#L393) and [:660](https://github.com/crackededed/Xtra/blob/0ab697de04799365f590f91e2dfbefc092c3ad5a/app/src/main/graphql/schema.graphqls#L660); FrankerFaceZ's Add-Ons "Deck" live-followed column, a browser extension that runs inside the twitch.tv page, also passes `$sort: StreamSort` to it: [followed.gql](https://github.com/FrankerFaceZ/Add-Ons/blob/8bd95a3ae9d82755ecbc536b152b3c6ccd9a224c/src/deck/columns/live/followed.gql), defaulting to `VIEWER_COUNT`: [followed.js:71](https://github.com/FrankerFaceZ/Add-Ons/blob/8bd95a3ae9d82755ecbc536b152b3c6ccd9a224c/src/deck/columns/live/followed.js#L71)). Two points limit what that proves:
- Xtra's own followed-streams query passes no sort and re-sorts by viewer count on the device ([FollowedStreamsDataSource.kt:78](https://github.com/crackededed/Xtra/blob/0ab697de04799365f590f91e2dfbefc092c3ad5a/app/src/main/java/com/github/andreyasadchy/xtra/repository/datasource/FollowedStreamsDataSource.kt#L78)), so it does not use server order. It re-sorts and uses `viewersCount`.
- `RELEVANCE` is a real value on the game directory query, where TwitchDropsMiner sends it with a `recommendationsContext` (READ: [constants.py:414](https://github.com/DevilXD/TwitchDropsMiner/blob/99d12fd2d815d7737258ed57405c63c0686bd3e1/constants.py#L414)). That matches the "Twitch's recommendations" directory sort in the page above. That `followedLiveUsers(sort: RELEVANCE)` returns a personalised order for follows is INFERRED, untested, and no source I read shows it returned.

Whether follows reads under the web client id need one: UNCHECKED.

## Q4. Risks

**Terms: the Developer Services Agreement loaded.** `curl --compressed` returns the page text (the earlier fetches returned only navigation). Last modified 2024-12-04 (READ: https://legal.twitch.com/legal/developer-agreement/). Section XI "Developer Representation and Warranties", item I, in full:

> "You will not access undocumented Program Materials or otherwise attempt to derive or use the underlying source code of undocumented Program Materials without Twitch's prior written permission. You may only access data from Program Materials consistent with the terms of this Agreement and, unless you have Twitch's prior written permission, will only access Program Materials documented on the Twitch Developer Site."

"Program Materials" is defined in §II.A.3 as software, APIs, services, documentation, data and the like "made available under this Agreement to you by or on behalf of Twitch". The agreement binds "your use of the Program Materials" and anyone who registers an app. Section IV.C bars circumventing "other controls that limit use of the Program Materials". Whether GQL is "undocumented Program Materials", and whether Streams, which registered an app, is bound for GQL calls made with the public web client id, is an interpretation. INFERRED: the straightforward reading is that GQL is undocumented and the clause is aimed at it. That is a legal question, not mine to settle.

The general Terms of Service (last modified 2026-08-12, READ: https://legal.twitch.com/legal/terms-of-service/), Prohibited Conduct item xi, bars accessing the Twitch Services "by means of any robot, spider, scraper, crawler, or other automated means for any purpose, or bypass any measures Twitch may use to prevent or restrict access". Item vi bars circumventing "security-related features". Streams already calls GQL signed-out for playback and VODs (D-030 in `docs/DECISIONS.md` records that risk as accepted for the signed-out case); sending a user's first-party token would add the account itself to that exposure, which is the new part.

**Breakage history.**
- Hash change: in November 2025 streamlink's playback call began failing with `PersistedQueryNotFound`; a maintainer traced it to the `PlaybackAccessToken` hash and posted a fix in the thread; whether and when it shipped I did not check ([streamlink issue #6719](https://github.com/streamlink/streamlink/issues/6719), READ).
- Integrity: in June 2023 Twitch added Client-Integrity and a bot-protection layer; Xtra's maintainer said "that's just for the web client id. there's other ids that still work" and later added in-app integrity tokens ([Xtra issue #302](https://github.com/crackededed/Xtra/issues/302)). In February 2026 the maintainer wrote that "the old method for logging in was patched" and now gives "Unauthorized access", and that the TV sign-in is used because it has no integrity checks ([issue #885](https://github.com/crackededed/Xtra/issues/885)).
- Redirect: in April 2023 an OAuth redirect mismatch broke Xtra's first-party sign-in until the maintainer moved to another client id and redirect ([issue #271](https://github.com/crackededed/Xtra/issues/271)).
- Rate: TwitchDropsMiner caps its GQL use at 5 requests per second and notes that "GQL is pretty volatile and breaks everything if one runs into their rate limit" ([twitch.py:521-523](https://github.com/DevilXD/TwitchDropsMiner/blob/99d12fd2d815d7737258ed57405c63c0686bd3e1/twitch.py#L521)).
- Documentation: the community GQL document warns that using the API "may lead to consequences" tied back to the user ([README](https://github.com/mauricew/twitch-graphql-api/blob/3e376e51/README.md), written about 2018–2022).

**Account action: weak evidence.** TwitchDropsMiner has two issues where users reported suspensions after using it. In [#730](https://github.com/DevilXD/TwitchDropsMiner/issues/730) the notice, as transcribed by the maintainer, cites chat spam from an automated account, which the miner cannot do; the maintainer disputes the link and says it was one other report in seven months. In [#870](https://github.com/DevilXD/TwitchDropsMiner/issues/870) the maintainer says the user had been "tinkering around with the Twitch API". I read the issue bodies and the first replies only. These show reports exist; they do not show GQL use caused any suspension.

## Q5. What Streams can show with its own token, and what closer costs

With our own Client ID and a user token carrying `user:read:follows` (Helix only):

- **Live now:** name, title, category, viewers, start time, thumbnail, tags. Order: descending viewers, set by Twitch.
- **Offline follows:** name and follow date from Get Followed Channels, newest follow first. Optional: newest VOD time from Get Videos, one request per channel, as a "last streamed" proxy.
- **No** Twitch "recommended" order, no sponsored-first order, no per-follow notification state, no "new videos" count (INFERRED from the endpoints' fields; Frosty and Chatterino, which only use Helix, show nothing more).
- Streams can add an order Twitch's API cannot: rank the live follows by Streams' own history of what the operator opened (the "People" model in the discovery note §4), which is closer to "likely to watch" for this person than Twitch's sidebar, and works across platforms.

What each step toward Twitch's own order would cost:

1. **GQL for follows with the signed-out public web client id:** not possible; follows need an account (INFERRED, since GQL's `currentUser` is the signed-in user and I made no request).
2. **GQL with a first-party token captured from a device-code sign-in as the TV client:** what Xtra does. Costs: a second sign-in for the operator, Terms exposure on the account (Q4), breakage when hashes or client ids change, and our not owning that client id. It gets `lastBroadcast`, notification state and possibly `sort: RELEVANCE`, none confirmed.
3. **Web-client token plus Client-Integrity:** needs a browser to compute the token (streamlink uses headless Chromium; Xtra uses a WebView); a plugin inside IINA has no browser to run it in, and Xtra's maintainer says its older login method was patched (issue #885) while the TV sign-in has no integrity checks.
4. **Reading the operator's twitch.tv cookie:** not an option (`docs/design/DISCOVERY-AND-PLATFORMS-2026-11-22.md` §2.3).

## Recommendation

Take A, B, C and D with E on top, and do not build F or G for this feature. Reasons, each with its basis:

- A and B give the operator's actual follows with real status and order, with one new scope. That is the documented, lowest-risk path and already half-built (`src/twitch-helix.js`).
- The only thing F and G add over A to D is Twitch's own order and a few fields, and no source I read shows that the personalised order is reachable at all (INFERRED from absence: nobody I read passes `RELEVANCE` for follows, and Xtra re-sorts by viewers), so the cost buys an unconfirmed return.
- E answers the operator's question about "implicit priority" better than Twitch's sidebar can for this use, because it ranks by what this operator opens.
- If the operator wants to try F, the step that would decide it is one signed-in observation of what `followedLiveUsers(sort: RELEVANCE)` returns, made by the operator under their own token in a development build. That falls under the operator's approval (AGENTS.md: no account authorization without the operator), and I did not run it.

Load-bearing assumption: the operator wants usefulness of order more than parity with twitch.tv's order. What would flip it: the operator preferring an exact match of the sidebar over documented-only APIs, or a test showing `RELEVANCE` ordering is a strong signal.
